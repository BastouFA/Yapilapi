# Web app: languages and translation status

The web app (`apps/web`) ships four languages. English is the source of truth; the others are drafts.

| Locale | Direction | Coverage                                                                            | Status                                                |
| ------ | --------- | ----------------------------------------------------------------------------------- | ----------------------------------------------------- |
| `en`   | LTR       | Every string                                                                        | Reviewed                                              |
| `fr`   | LTR       | Navigation, auth, forms, errors, feed, settings core, Messages and Communities core | **Machine-drafted, needs review by a native speaker** |
| `ar`   | RTL       | Same core set, six plural forms                                                     | **Machine-drafted, needs review by a native speaker** |
| `yo`   | LTR       | Same core set, no plural distinction                                                | **Machine-drafted, needs review by a native speaker** |

Search, Discover extras (trending/NOW/people-to-follow/explore), Notifications, Moments, Events, Places and
Business (English-complete: `en-search.ts`, `en-discover2.ts`, `en-notifications.ts`, `en-media.ts`,
`en-events.ts`, `en-places.ts`, `en-business.ts`) only have a **small hand-picked draft** in `fr`/`ar`/`yo`
(nav labels, page titles, and the one or two primary actions per screen) — every other string in those
namespaces falls back to English at runtime by design. This is an explicitly accepted gap, not an oversight:
finish translating them before launch, in the same files.

## How it works

- Catalogs live in `apps/web/src/i18n/messages/`. `en.ts` merges `enBase`, `en-pages.ts`, `en-social.ts` and the
  per-area files above; each other language is a `Partial` of the English keys (`fr.ts` + `fr-social.ts`, and so on).
- A key missing from a draft language falls back to English at runtime, so nothing is ever blank.
- `t('key', { name })` derives its parameters from the `{placeholders}` in the English text. Plurals are objects (`zero/one/two/few/many/other`) resolved with `Intl.PluralRules` for the active locale.
- `catalogs.test.ts` enforces: no empty strings, plural objects always define `other`, every `t('literal')` used in the source exists, drafts only use existing keys, drafts keep exactly the same placeholders, plural categories are valid for the locale, and the core keys are translated.
- Dates, numbers and relative times use `Intl` with the active locale. Arabic switches `<html dir="rtl">` and all CSS uses logical properties (`inline-start`, `padding-inline`, ...) so no separate RTL stylesheet exists. Icons that imply direction flip in RTL.
- Server messages from the API are English only. The web app localises the ones it knows (denial reasons such as `teen_friends_only`, feed "reasons") and shows the API text for other 4xx errors.

## Before launch

1. Have a native speaker of each language review every file named `*-social.ts`, `fr.ts`, `ar.ts`, `yo.ts`. Pay attention to: tone (informal vs formal "you"), Arabic plural forms and gender agreement, Yoruba tone marks and diacritics.
2. Translate the remaining English-only strings (settings detail pages, community creation help texts, error copy).
3. Localise the API's user-facing messages (they are English only), or return stable error codes for every case.
