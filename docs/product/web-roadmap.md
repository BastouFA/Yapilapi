# Web app: what exists and what is next

## Implemented (first vertical slice, all against the real API)

- **Accounts**: sign up (with age-aware rules), email verification, sign in with two-factor, password reset, sessions in an httpOnly cookie, server-verified auth guard.
- **Feeds and posts**: For You / Following / Friends / Communities / Local, explainable "why am I seeing this", post composer (audience, circles, poll, topics, link, location opt-in), comments and replies, reactions, saves, sharing, feedback controls.
- **People**: profiles, follow / friend / block / mute / restrict, followers and following lists.
- **Settings**: profile, privacy, attention (daily limit, quiet hours, focus mode), display (language, theme, motion, contrast, low-bandwidth), security (two-factor, sessions), connections, account (deactivate, delete).
- **Inbox** (new): conversation list with unread badges, pinned and muted states; chat with realtime delivery over the WebSocket ticket flow (typing, "Seen", reconnect with catch-up); replies, reactions, delete-for-everyone; optimistic sends with idempotent retry; new message by username or from a profile; group creation from friends or usernames; group details (rename, add and remove members, mute, pin, leave); teen contact rules explained in plain language. The Inbox nav item shows the unread count.
- **Communities** (new): browse and search public communities, joined list, invitations (accept / decline), create (visibility, join policy, topics, rules; teens are limited to private), community page with posts (and a community composer for members who can post), channels (list, create, chat in real time), members (and approve / decline requests for managers), about and rules; join, request to join and leave states.
- **Search** (new): natural-language search box across people, creators, posts, videos, communities, events, places, businesses, products and topics; an overview mode (a few results per type, "show all") and a focused, paginated mode per type; recent-search history with clear; parsed-filter chips ("near me", a time window, party size, a price hint) reflecting what the API understood, with an honest notice when it fell back to plain keyword matching.
- **Discover** (extended): For You (topic picker, unchanged) plus Trending (time window, trending topics, trending posts), People to follow, NOW (nearby events / active communities / approximate nearby-people and -places counts, gated by the API's own `live.enabled` and k-anonymity rules, never assumed client-side), and Explore topics.
- **Notifications centre** (new): paginated, filterable (unread-only, category) inbox with per-item mark-read / delete and mark-all-read; realtime unread badge in the nav (reusing the existing WebSocket connection); a settings tab for quiet hours, focus mode, pause-for-a-while, and per-category per-channel (in-app / push / email) toggles, all server-enforced (the UI reflects locks such as the teen default quiet-hours window, it never overrides them).
- **Media and Moments** (new): photo/video/audio attachments in the post composer (client-side size/type checks, alt text, per-file upload progress and retry); Moments — a tray on the home feed, create (photo/video/text/audio, caption, visibility including circles and a selected-people picker, expiry incl. a custom time, opt-in approximate location), and a fullscreen viewer (progress bars, keyboard and swipe-zone navigation, reactions, viewer list and delete for the author, expired/not-found states). Video and audio never autoplay; they need an explicit tap on native controls.
- **Events** (new): browse with filters (search text, online, free) and near-me, and "mine" tabs (hosting, going, interested, waitlist, saved, invited, past); detail page with RSVP / waitlist / withdraw, save, copy-link share, an `.ics` calendar download, attendees, ticket types (read-only, since checkout is not part of this slice), a check-in code once you are going; create / edit (teens are limited to friends, community or private events, no paid tickets); host tools (add / remove co-hosts, add ticket types); publish, cancel (with a reason shown to attendees) and delete.
- **Places** (new): browse / near-me with type, open-now and rating filters; detail page with hours, photos, upcoming events there, reviews (write, report, owner replies, a "pending safety check" notice), save, and a claim-for-a-business flow; add-a-place form (teens cannot add places).
- **Business** (new): directory with search and a verified-only filter; profile with about / posts / events / offers / services tabs, follow / unfollow; a booking flow (choose a bookable place or service, date, party size, duration, notes) against the business's own booking settings, an auto-confirm notice when it applies, and a view of the customer's own upcoming bookings for that business with cancel.
- **Commerce** (new): a `/shop` area — browse (search, product-type filter) and product detail (media, stock/rating, returns policy, verified-purchase reviews); checkout for a single product (server-priced order creation, a shipping-address form for physical items, and payment with an opaque payment-method token — never a raw card field; the dev payment provider's test tokens stand in for a real card element, see "API gaps" below); orders (buying and selling tabs, a shared buyer/seller detail view with cancel / confirm receipt / mark fulfilled / retry payment, tracking); refunds (buyer request, seller or staff approve/deny) surfaced on the order itself; a seller dashboard (create/list products, seller orders, refund decisions, payout account setup, balance, request a payout). A "Shop" nav entry was added.
- **AI assistant** (new): a `/ai` area — chat with the assistant (streamed-style turn history, sources shown alongside a reply, safety notices from the API surfaced as-is); every draft the assistant proposes (a post, a reply, a message, …) is never applied automatically — it lands in a review list where the person can edit the text, confirm/publish it as an explicit action, or discard it; a memories view (list, edit, forget) so the person can see and correct what the assistant has retained about them; a usage view (quota/limits as the API reports them). Confirm is the only path that turns a draft into a real post/message; there is no auto-apply anywhere in this UI.
- **Privacy centre** (new): a `/settings` "Privacy" section covering data export (request, poll status, download when ready), account deletion (explicit confirm, cancel-while-pending), consent toggles as the API defines them, blocked/muted lists with unblock/unmute, and active sessions with per-session sign-out — all mirroring exactly what the API reports rather than a client-side guess.
- **Creator economy** (new): a `/creator` dashboard for running a creator business — become a creator / KYC status, subscription plans (create/list), subscribers (view, remove), the creator's own fan subscriptions, payouts (balance, request), revenue, supporters (tips/gifts received), affiliate links and conversions, and brand partnerships (propose → negotiate → accept/decline → in progress → deliverables → paid, with mandatory sponsored-disclosure carried through from the API). Teens are blocked from becoming creators in the UI, matching the API rule.
- **Studio** (new): a `/studio` area for non-destructive video/audio editing — upload media into a project, edit its recipe (segments, aspect, crop, thumbnail, captions), caption tracks (manual, imported or machine-transcribed), render (ffmpeg-backed, with a clear "not available" notice when the render service is down), AI suggestions (title/description/thumbnail/silence-cuts/highlights/captions-review) that are proposals only until explicitly accepted or dismissed, and publish (now or scheduled) gated behind an explicit confirmation dialog, with the current publication and a cancel-while-scheduled action.
- **Live** (new): a `/live` area for interactive live sessions — browse on-air/scheduled/ended sessions and "my sessions"; schedule and start a session (public/followers/subscribers/private visibility, interactive or video media mode); a session room with chat (send, moderator remove, aggregate reactions), polls (open/vote/close), Q&A (ask/upvote/answer/dismiss), a shop tab (host's own products, one pinned at a time), and, for the host/co-hosts/moderators, team management, moderation (mute/ban with a reason) and settings (chat on/off, slow mode, blocked terms); ending or cancelling a session is gated behind an explicit confirmation dialog.
- **Memory** (new): a `/memory` area — "my memories" (collections, browse/search, create, edit, delete), a personal timeline across posts/moments/Reals/events/shared experiences (filterable by item type), on-this-day suggestions from earlier years and detected-trip suggestions (both computed on the fly and only ever turned into a private memory by an explicit "save" action, never automatically), and, per memory: items and people/place/event/trip/community/experience links (add/remove), a deterministic non-AI recap (counts, date span, places, people) with a "save as summary" action, optional AI drafts for a title/summary/highlights (never applied until an explicit confirm, editable first, each gated behind a `ConfirmDialog` exactly like the AI assistant's own drafts), and a photo-slideshow video export with a clear "not available" notice when the server has no video-processing tool configured.
- **Real** (new): a `/real` area for dual-camera authenticity captures — a friends' tray (last 48h, grouped per author), "my Reals" (capture via front/rear photo upload, caption, visibility), authenticity indicator badges as the API computes them, reactions, an explicit share-to-profile action (separate from capturing, carries the authenticity receipt), delete gated behind a `ConfirmDialog`, and opt-in, off-by-default, quiet-hours-aware reminders (day/time/timezone).
- **Together** (new): a `/together` area for shared experiences — joined/invited tabs, create (title, description, visibility), accept/decline an invitation, a merged chronological timeline of every member's own perspective (text/media/one of their own Reals), inviting members and suggested invites (people who also attended a linked event), a cover photo (pin/vote), leave (with an explicit "keep my contributions" choice) and owner actions (close/reopen/archive/delete) all gated behind `ConfirmDialog`, a per-member "show on my profile" opt-in, and an explicit "export as memory" action.
- **Developer console** (new): a `/developer` area — register apps (up to 10 per account, adults only, matching the API's teen restriction), a client secret shown exactly once at creation with an explicit "I've stored it" checkbox gating the dialog's close button (mirrors the existing MFA recovery-codes dialog pattern) and never re-displayed after; per-app API keys (scopes, rate limit, optional expiry) issued the same shown-once way, with revoke; webhooks (URL, event subscriptions, description) with their signing secret also shown once, test-event send, re-enable after the API's auto-disable, secret rotation, and a delivery log (status, attempts, HTTP status code, error) per endpoint; an edit tab for app details and redirect URIs; delete (app, with all its keys/webhooks/authorizations) and secret rotation both gated behind `ConfirmDialog`.
- **Quality**: keyboard and screen-reader support, axe checks in light, dark, Arabic RTL, phone width, low-bandwidth and high contrast, strict CSP with a per-request nonce, no tokens in browser storage.

## Intentional gaps (not built yet)

- Terms of Service and Privacy Policy pages (sign-up links need real pages).
- Voice and video calls and shared plans in chat (API exists).
- Editing a sent message (API supports it), forwarding, message search, read receipts per member in groups.
- Community administration: roles and permissions, banning and removing members, editing settings, inviting people, archiving channels, events and resources.
- Paid communities and creator monetisation.
- Push notifications and installable app.
- Resumable/chunked media upload (`docs/architecture/media.md` describes it for large video/audio); the web app only wires the simple single-request upload, so a very large file simply hits the API's size limit instead of resuming.
- Search's product result rows now link to the commerce product-detail page; its topic result rows are still unlinked (Discover's "Explore topics" only lists topics, it does not link into a per-topic page either).
- Commerce checkout only covers a single product bought straight from its detail page (`items: [{productId, quantity: 1}]`); there is no cart for multiple products or sellers in one order, even though the order API itself accepts several line items. Ticket purchase for paid events and business "book a service" beyond a request still stop at "not available in this preview" / "requested, wait for confirmation" — the same order/pay endpoints they would need are exercised by Commerce, but the Events and Business screens are not wired to them in this pass.
- Commerce gaps: no product creation image/file upload UI (the seller dashboard's "new product" form covers physical/service/digital/booking basics only, no media or digital-file attachment, no product editing or deletion, no product-linked posts); shipping is the API's flat per-product placeholder (no address validation, no carrier rates) and tax is the seller-declared flat rate, both shown as-is; no staff views (fraud review, disputes, reconciliation) since those are staff-only in the API; disputes beyond a refund are not shown anywhere in the web app (a disputed order only shows its status badge); the payment-method picker is a dev-provider test-token dropdown, not a real Stripe Elements card widget (see "API gaps" below).
- No screen to create a business profile (only browse, follow and book existing ones); Places' claim flow tells a person to create one first, which they cannot yet do from the UI.
- Event host tools cover adding co-hosts and ticket types, but not removing/archiving a ticket type or changing a co-host's permissions.
- fr / ar / yo have only hand-picked draft coverage of the new Search / Discover / Notifications / Media / Moments / Events / Places / Business strings (documented in `docs/product/i18n.md`); everything else in those namespaces falls back to English at runtime, which is expected and by design, not a bug. The same applies to the newer `ai.*` / `privacy.*` / `creator.*` / `studio.*` / `live.*` / `memory.*` / `real.*` / `together.*` namespaces below — English only for now. `together.*` was kept as its own namespace rather than folded into `real.*`, matching the API's own separate `real`/`together` modules and gate flags (`REAL` vs `REAL_TOGETHER`) despite the similar naming.
- Creator economy is built as the "run your own creator business" dashboard only; fan-facing subscribe/tip/gift actions are not wired into the profile pages (`ProfileView.tsx` / the business profile view), since those pages were being actively edited by the Commerce build in parallel — a fan can see and manage subscriptions they already have from `/creator`, but cannot start a new tip/gift/subscription from someone else's profile in this pass.
- Studio's recipe (EDL) editor is a raw JSON textarea with validate/save, not a visual timeline; markers, clips, attaching a recording to a project, translation, and all staff-only endpoints are not built.
- Live's room UI uses interval polling (4-5s, `usePoll`) for chat/polls/questions rather than the dedicated `/v1/live/:id/ws` realtime socket — a deliberate, bounded, testable stand-in documented here rather than either skipping live updates or building a bespoke WebSocket client mid-way through this build. `GET live/:id/commerce` (gift/subscribe entry points), markers/clips/recording/translate extras, and staff-only endpoints are not built.
- Memory's item/link pickers are plain "type + ID" fields, not a visual picker into your own posts/moments/Reals/events; adding an item you don't already know the ID of means finding it elsewhere first. Reordering items (the API's `PUT .../items/order` endpoint) and the timeline's person/place/event filters are not wired into the UI, only the type filter is.
- Real: no separate single-capture detail page (reactions/share/delete are inline on the tray/mine list rows only); no circle/selected-audience picker UI for the `circle`/`selected` visibility options — `circleId`/`audience` fields exist on the API but the UI only offers the visibility dropdown itself, not a way to pick who "selected" or a "circle" means; capture creation is plain `<input type="file">` uploads (no live camera capture, since a browser tab has no equivalent of a native front/rear dual-camera API), and `attestation.available` is always `false` in this dev environment since no App-Attest/Play-Integrity verifier is installed (the UI shows whatever the API reports, honestly, rather than faking it) — the same "honest not-available notice" pattern as Live's video mode and Studio's render service.
- Together: contributions (media/Real/text) are added by plain "ID" fields rather than a picker into your own media or Reals, matching Memory's item/link pickers above; inviting a member is by user ID rather than a friend-search picker; cover-photo pin/vote both call the same `setCover` endpoint from the UI (the API differentiates owner-pin from member-vote server-side by role, so the client does not need two code paths); "my sessions"-style filters beyond joined/invited (e.g. archived) are not exposed as separate tabs.
- Developer console is scoped to what the coordinator asked for: apps, API keys, webhooks and their delivery log, scopes. Not built: the OAuth 2.0 authorize/consent screen and grant management for a third-party app to actually use these credentials against a user (users still manage grants they've _given_ under Settings > Privacy > Connected apps, unaffected by this build); the public API explorer; mini-apps (catalog, review, install — the `MINI_APPS` flag is off anyway, see `docs/security/developer-platform.md`); per-app usage analytics or billing (the API has none yet either). API key scopes are a single fixed checkbox-of-one today (`public:read` is the only scope the API defines), so the create-key form doesn't need a scope picker beyond that; it will need one if the API grows write scopes. Redirect URIs are editable as a plain newline-separated textarea, not validated client-side against the API's https/no-wildcard rules (the server still enforces them; a bad URI simply comes back as a form error).

## API gaps found while building

- Only conversations that exist when the socket connects (or that the server announces with `conversation.added`) are pushed. A newly created direct conversation, or a group the creator just made, is not subscribed for the creator, and the recipient of a new direct conversation gets only a generic `notification` frame without a conversation id. The web app works around it by subscribing explicitly and refetching the inbox on message notifications; a `conversation.added` event to both sides on creation would remove the workaround.
- Error messages and feed reasons are English strings; stable codes for everything would allow full localisation.
- No suggestions or search endpoint for people (the "add people" pickers use friends and exact usernames).
- For You excludes the viewer's own posts, and topics are returned as display names but accepted as slugs on write.
- Production cookies across sub-domains need an explicit cookie domain setting.
- Not an `apps/api` bug, but worth recording: the hand-written `@yapilapi/api-client` type for `GET /v1/events/:id/share` had drifted from the real handler (`{url, icsUrl}` vs. the actual `{url, calendarUrl, title, text, audience, note}`), and `BookableInfo`'s `places`/`services` were missing the `timezone`/`hasHours` fields the API actually returns. Both were fixed in `packages/api-client/src/{client,types}.ts` while building Events and Business; the API itself was correct.
- `@yapilapi/api-client`'s `RequestOptions` had no way to send a per-call header, so `createOrder` / `pay` / `requestRefund` / `requestPayout` (all of which the API requires an `Idempotency-Key` header for) had no way to send one. Added an optional `headers` field to `RequestOptions` (`packages/api-client/src/http.ts`), merged over the client's global headers; commerce/payments calls generate a fresh key by default and accept an explicit `idempotencyKey` for a caller-controlled retry. Not an API bug — the API's contract was already documented in `docs/architecture/payments.md`; the client just hadn't grown a commerce namespace yet.
- The web checkout necessarily uses the `dev` payment provider's fixed test tokens (`tok_success`, `tok_decline`, …, see `docs/architecture/payments.md` "Dev provider") behind a plain `<select>`, since this repo runs `PAYMENT_PROVIDER=dev` and a real Stripe Elements/Payment Element widget needs a live publishable key and Stripe's JS SDK that this environment does not have (see "What needs real provider credentials" in the same doc). The select is wired through the same `paymentMethod` field the real widget would populate, so swapping it in later is a UI-only change.
